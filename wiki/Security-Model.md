# Security model

openvc verifies Verifiable Credentials, handles signing keys, and dereferences
issuer-named URLs over the network. This page states what it defends, against
whom, and how — the reference an auditor (or an integrator) starts from. The
per-control hardening notes are in
[SECURITY.md](https://github.com/luisgf/openvc/blob/main/SECURITY.md); the
code-cited auditor annex (per-parser tables, the fail-closed invariants catalog,
the residual-risk register, and the fuzz-coverage / adversarial-review history)
is the [external-audit pack](https://github.com/luisgf/openvc/tree/main/docs/audit).

## Assets

- **The verification decision.** The accept/reject output of `verify_credential`
  (and `verify_ebsi_badge`) is the asset everything else protects: a *wrong accept*
  (a forged/tampered/expired/revoked credential accepted) is the primary harm.
- **Signing keys.** Private key material. openvc never requires it in-process on the
  signing path — signing goes through the `SigningKey` protocol, so an HSM/Vault/KMS
  backend keeps keys out of the process (see [Keys & HSM backends](Keys-and-HSM)).
- **Trust anchors.** The roots a verifier trusts: X.509 `x5c` trust anchors, the
  EBSI RootTAO, the DID documents a resolver returns. Compromise of an anchor is
  out of scope (it is the operator's root of trust) but openvc must not *widen* it.

> **On the issuer side.** The OpenID4VCI **key-proof verifier**
> ([ADR-0007](https://github.com/luisgf/openvc/blob/main/docs/adr/ADR-0007-oid4vci-issuer-side.md))
> adds the mirror attacker — one who *requests* a credential rather than presenting
> one — as a row in the table below. The asset is unchanged: it is still a verification
> decision over attacker-controlled bytes. The issuance *decision* is **not** openvc's;
> the protocol layer and single-use enforcement of `c_nonce` live in the consuming
> application, injected as a required callable, so a caller whose store is not atomic
> re-opens a replay window openvc cannot close for them.

## Trust boundaries

Untrusted input crosses into openvc at:

1. **The credential itself** — fully attacker-controlled bytes (a JWS/SD-JWT string
   or a JSON document). Every field is untrusted until the signature verifies.
2. **Network dereferences** — `did:web`, `/.well-known/jwt-vc-issuer`, status-list
   and `credentialSchema` URLs. The *issuer* names these URLs and (for status/schema)
   controls the bytes returned. All of these are attacker-influenced.
3. **The `SigningKey` / key-agreement backend** — an out-of-process boundary (HSM,
   Vault, KMS). openvc trusts it to sign/decrypt but not to hold key material for it.
4. **Injected resolvers** — `resolver`, `resolve_status_list*`,
   `resolve_credential_schema`, `*_fetch`. openvc's guarantees hold only for what
   these return; a custom resolver that skips verification or the SSRF guard opts
   out of the corresponding control (hence the blessed defaults in `openvc.resolvers`).

## Attacker capabilities & controls

| Attacker capability | Threat | Control |
|---|---|---|
| Present a forged / tampered credential | Wrong accept | Signature verification through the matching suite; the `{ES256, ES384, EdDSA, Ed25519}` **allow-list runs *before* any crypto** (rejects `alg:none`, RS\*, HS\* — alg-confusion defence); unknown JWS `crit` extensions are rejected on every JOSE lane (RFC 7515 §4.1.11, parity with the COSE and JWE paths); JWS is R‖S, never DER |
| Name an arbitrary issuer but sign with own key | Impersonation | **Issuer binding** — a Data Integrity proof's `verificationMethod` must be controlled by the credential's `issuer` DID; VC-JWT reconciles the JWT envelope with the embedded credential, and so does SD-JWT for a W3C credential (a VCDM payload, whatever its issuer `typ`: `iss` must match `issuer`); x5c binds the leaf SAN to `iss`. A W3C SD-JWT whose issuer JWT has no `iss` member and a W3C `typ` (or none) is keyed on the `issuer` of its body instead (VC-JOSE-COSE §4.2; a disclosed `issuer` is never used, a present `iss` that is `null` or empty is not replaced, a `dc+sd-jwt` still needs `iss`), and that value is unauthenticated until the signature verifies, exactly like `iss`: it only selects the key to try. Such a token has no `iss` in `result.claims`. On every lane `result.issuer` is the authenticated issuer, the identifier whose key verified |
| Re-spell a signed RDF Data Integrity credential's JSON without changing its signed dataset (a member keyed by its IRI or an alias, an inline `@context` that re-maps a term, a term no context defines, `@included`, an array nested in an array such as `credentialStatus: [S1, [S2]]`, a status entry moved under another property that also names it, a trusted context dropped and its terms spelled through an inline `@vocab`), or have an issuer sign a value its term cannot carry (an untyped `validUntil` under its IRI) | The policy reads JSON the signature does not cover: an expiry, status or schema check skipped, a spoofed `credentialSubject` passing holder binding, unsigned claims | **Context validation** (VC-DI §2.4.1) after the proof verifies, and before signing, on `eddsa-rdfc-2022`, `ecdsa-rdfc-2019` and `ecdsa-sd-2023`. The VC base context must come first, followed only by trusted context URLs or `@vocab`-only objects. The document and its proof must be the compacted form of their own expansion, with no `@included`/`@reverse`, no second description of the document node and no array directly inside an array (outside a `@list`), every member or `type` value that any context the loader serves defines (bundled or `extra_contexts`, whether or not the document lists it) must be spelled by its term (the VC base context's own term where it has one, so an injected alias is refused), and an entry of the top-level `credentialStatus` may not be described anywhere else in the document, a nested node's `credentialStatus` included. The status check refuses a `credentialStatus` array member that is not an object, or an entry with no `type`, rather than skip it ([details](Data-Integrity#the-json-must-be-what-was-signed)) |
| Serve a malicious document at a fetched URL | **SSRF** (reach internal hosts / cloud metadata) | `openvc.fetch`: https-only, blocks private/loopback/link-local/reserved/multicast IPs, refuses redirects, **pins the connection to the validated IP** (closes DNS-rebinding). Status/schema fetches use the same guard via the blessed `openvc.resolvers` defaults |
| Send JSON nested thousands of levels deep (a token payload, a disclosure, a DID document, a `vp_token`, or a dict handed to `verify_credential`) | **Batch abort** (a bare `RecursionError` from `repr()` / `==` on the deep value aborts a whole `verify_many`) | Untrusted JSON is refused past **100** levels of nesting where it enters, with the format's own typed error. Objects handed over already parsed, including those an injected fetch returns, are held to the same bound, and `verify_many` isolates the item |
| Host a DID document that is valid JSON but the wrong shape (a `null` or scalar `verificationMethod`, a relationship that is not an array, a `didDocument` wrapper that is not an object, a method whose `id` is not a string) for the `did:web` / `did:webvh` issuer an unsigned token names | **Batch abort** (a bare `TypeError` / `AttributeError` from the parser aborts a whole `verify_many`), and a wrong-typed relationship read as "not declared" would leave the key purpose unenforced | `parse_did_document` raises `DidResolutionError` for a wrong-typed container (the pipeline reports `KeyResolutionFailed` for that item on the JOSE lanes and `KeyResolutionError`, which is also a `ProofError`, on the Data Integrity lanes, sync and async alike) and never reads it as absent; an entry without a string `id` is dropped and selects no key or purpose. The same parser serves `did:web`, `did:webvh` and the EBSI DID Registry |
| Put a JSON array or object where a string is expected (a JOSE `alg` or `typ`, an SD-JWT `_sd_alg`, a KB-JWT `alg`, an `ldp_vc` `cryptosuite`, an OpenID4VCI key-proof `typ`, a Data Integrity `proofPurpose`) | **Batch abort** (the allow-list membership test hashes the value; an array or object is unhashable, so a bare `TypeError` aborted a whole `verify_many` before any signature check) | Each of these checks type-checks the value first. Every lane but `proofPurpose` raises the class a disallowed string already gets there (`UnsupportedAlgorithm`, `SdJwtError`, `UnsupportedPresentationFormat`, `ClaimsInvalid`), so `verify_many` / `verify_many_async` isolate the item. A non-string `proofPurpose` is `ProofMalformed` before the DID is resolved (a wrong string stays `ProofPurposeMismatch`), and `DidDocument.key_for_purpose` returns `None` for one. The error messages name a container by its type (`list`, `dict`), never its `repr()`, so a deep array cannot overflow the stack while the error is being built. Tests pin each lane with an array, an object and an array nested 90 levels (96 for the `ldp_vc` `cryptosuite`, 98 for the Data Integrity `proofPurpose`, whose enclosing objects bring the input to the cap itself), within the loader's 100-level cap |
| Put a lone UTF-16 surrogate (`\ud800`) in a Data Integrity credential, an `ecdsa-sd` disclosure, a `did:webvh` `updateKeys` entry or an OpenID4VCI request | **Batch abort** (JSON allows the escape and the parsed `str` has no UTF-8 form, so an unguarded encode raised a bare `UnicodeEncodeError` that aborted a whole `verify_many`, with no valid signature needed: pyld hashes only a blank node's statements, so a credential whose subject has an `id` reached it) | Each lane raises its own class, so `verify_many` / `verify_many_async` isolate the item: `DataIntegrityError` on `eddsa-rdfc-2022` and `ecdsa-rdfc-2019` (also through `verify_vp_token`, a VP-JWT, the status-list second hop and the issuer side), `ProofMalformed` on `ecdsa-sd-2023`, `DidWebvhError` for an `updateKeys` entry (a multikey is ASCII), `CredentialRequestMalformed` / `MalformedToken` for an OpenID4VCI proof or key attestation (a compact JWS is ASCII), and `InvalidKey` for a JWK member in a thumbprint (`ClaimsInvalid` through `verify_credential_request_proofs`). The message names the code point and its index, never the text, and the string is never repaired, so two different inputs never hash alike. The JOSE lanes still accept a surrogate the issuer signed |
| Ship a tiny highly-compressible status list | **Decompression bomb** (OOM DoS) | Status decode caps the *decompressed* output at 16 MiB and fails closed (`StatusListError`), reading incrementally so a bomb is never materialised |
| Point `credentialSchema` at a schema with a catastrophic `pattern` | **ReDoS** (CPU DoS) | Schema validation is **opt-in**; remote `$ref` is off (no SSRF via `$ref`). Residual `pattern`-ReDoS is a documented limitation (mitigation tracked) — point the schema resolver at trusted hosts |
| Swap / replay a status list or presentation | Stale-status / replay accept | Status-list token `sub` must equal the fetched URI (anti-swap); presentations bind `aud` + one-time `nonce`/`challenge`; a fetched status list is **verified** before it is trusted. On SD-JWT VC with `require_key_binding=True`, the KB-JWT is verified even when the issuer JWT is expired, so an `EXPIRED` verdict is not a substitute for holder binding. A KB-JWT's `iat` is required and bounded both ways — no older than `kb_max_age_s` (default 300 s) at `now`, never future-dated (RFC 9901 §7.3 step 5.5) — the one freshness bound a stateless verifier owns, since nonce age is the caller's |
| Backdate / post-date validity | Expired/not-yet-valid accept | Temporal checks on `validFrom`/`validUntil` (+ VCDM 1.1 aliases) and proof `expires`, on every lane that carries a VCDM credential: Data Integrity, VC-JWT, and an SD-JWT whose payload is a VCDM credential (whatever its issuer `typ`), where the JWT `exp` only dates the signature (VC-JOSE-COSE §3.1.3). An IETF SD-JWT VC's claims are never read as that window. A **present-but-unparseable** timestamp fails **closed**, never silently skipped. `require_not_expired=False` waives only the credential's own expiry, never `nbf`/`validFrom` or a date the default policy refuses as malformed, and the suite that skipped the check reports it: `expired=True` exactly when the default policy would have rejected. The trust inputs openvc verifies for you are never waived: a status-list credential (through the blessed resolvers), a `JsonSchemaCredential`, an `x5c` chain. On the VC-JWT, SD-JWT VC (issuer JWT and KB-JWT), VP-JWT, status-list token and OpenID4VCI key-proof lanes a present `exp`/`nbf`/`iat` must be a finite JSON number, `null` included: `NaN`/`Infinity` would make every comparison false, i.e. *never expires*. A token at or past `exp` plus the leeway has expired; a future `nbf`, or an `iat` more than the leeway in the future, is rejected, and the expiry waiver covers neither |
| Replay a credential addressed to another relying party (VC-JWT or SD-JWT VC), also one a holder bound to you with a correct KB-JWT | Audience-restricted credential accepted by anyone who holds it (the KB-JWT's `aud` binds the holder's presentation, not the issuer's restriction) | RFC 7519 §4.1.3 on both VC-JWT lanes and on the SD-JWT VC issuer JWT: a credential with `aud` verifies only when the caller passes an audience that is in it ([ADR-0008](https://github.com/luisgf/openvc/blob/main/docs/adr/ADR-0008-jose-temporal-and-audience.md)). A VC-JWT without `aud` fails when an audience is expected; an SD-JWT VC without `aud` is unchanged, with or without one. Nested in a presentation, an SD-JWT VC is checked against the presentation's audience and a VC-JWT against `policy.audience`. A W3C credential secured as a JWS with no `iss` and no `typ` is refused as a bare JWS but reaches the SD-JWT lane once `~` is appended, and is held to the same rule there ([details](SD-JWT-VC#the-issuer-when-a-w3c-credential-has-no-iss)). An `aud` the issuer made disclosable and the holder withholds is invisible ([details](SD-JWT-VC)) |
| Withhold a selectively-disclosed `exp` / `nbf` / status / `cnf` / `vct` (or a W3C `validUntil` / `@context`) | Expired, revoked or not-yet-valid credential accepted: expiry or status skipped because a withheld disclosure looks like no claim at all | openvc's SD-JWT VC `issue()` **refuses** to make them disclosable through `disclosable` (draft-ietf-oauth-sd-jwt-vc-19 §2.2.2.3, plus `credentialStatus` and `@context`). `verify()` rejects a presentation that **presents** such a disclosure, or one of its sub-claims (`SdJwtError`), and rejects a payload that is not a VCDM credential and has no `vct`, since `vct` is REQUIRED (`ClaimsInvalid` for a `dc+sd-jwt`; a `vc+sd-jwt`, a draft-era `vc+ld+json+sd-jwt` or a token with no `typ` is accepted only as a conforming VCDM payload, a base context first in `@context` and a `type` that says credential, so a payload without one, a withheld `type` included, raises `SdJwtError`, and the typ alone never makes a payload VCDM). A **withheld** disclosure from a third-party issuer remains undetectable (RFC 9901 §9.7: it looks like a decoy). Check that the claims you rely on are present ([details](SD-JWT-VC#validity-claims-are-never-disclosable)) |
| Withhold a selectively-disclosed schema, or an `ecdsa-sd-2023` status | Skip a fail-closed gate | Documented caveat: an issuer that needs schema enforced on SD-JWT must keep it out of `disclosable`, and an `ecdsa-sd-2023` issuer must make status/schema **mandatory** pointers |
| Present a token as another kind of credential: an IETF SD-JWT VC as a W3C one (to skip its REQUIRED `vct`), or an SD-JWT issuer JWT with its `~` tail dropped as a VC-JWT (to skip key binding) | Type confusion: a token verified under the rules of another format | **Explicit typing.** A `typ` that is present on an SD-JWT issuer JWT must be `dc+sd-jwt` (an IETF SD-JWT VC, always with a `vct`), `vc+sd-jwt` or the draft-era `vc+ld+json+sd-jwt`: matched exactly and checked before any crypto, and anything else, `null` included, raises `SdJwtError`. The last two, and a token with no `typ` at all, are accepted only for a payload that passes two tests (these and no others): the **first** `@context` entry is a VCDM base context (VCDM 2.0 §4.3), not just a base URL somewhere in it, and the `type` includes `VerifiableCredential` and not `VerifiablePresentation` (§4.5, §4.13), so a holder that withholds a disclosable `type` is refused (#275). With no `typ` the `type` is also what tells a credential from a presentation. `dc+sd-jwt` has neither rule, and the lax base-URL test still decides its validity window and consistency checks. The VC-JWT lane refuses a JWS typed `sd-jwt`, `*+sd-jwt` or `kb+jwt` (RFC 8725 §3.11, #189) and, since 1.34.0, one whose payload carries an SD-JWT marker at any depth, a member named `_sd` or `_sd_alg` or an array-element digest object `{"...": …}` (`MalformedToken`, before the signature is checked; the names are RFC 9901 §4.1 item 7 and §4.2.4.2, where `_sd` and `...` are reserved and `...` is the array-element digest object, and §4.1.1, where `_sd_alg` is top level only), so an issuer JWT with disclosures cannot be stripped into a VC-JWT whatever its `typ` (#291). The VP-JWT lane applies both tests to the presentation (it did not read `typ` before 1.34.0). A token with no `typ` gives the first test nothing to refuse, so the SD-JWT lane also refuses one that carries a `vc` or `vp` claim (VC-JOSE-COSE §1.1.2.1, restated in §3.1.3), and none it accepts verifies as a VC-JWT once its tail is dropped. **Limit:** a zero-disclosure issuer JWT with no `typ`, a `vc` object and a `cnf` carries none of `_sd`, `_sd_alg` or `"..."` (an `_sd_alg` alone, or a decoy digest, is already refused) and still verifies as a VC-JWT, a lane that never enforces `cnf`. **Trade-off:** accepting a missing `typ` drops the explicit-typing guard (RFC 9901 §9.11) for VCDM payloads, because the W3C Recommendation makes the `typ` a SHOULD and its own examples omit it or use the draft-era name. The VCDM `@context`, the `type` check, the `vc` / `vp` ban, `require_key_binding=True` (a KB-JWT is still required) and the VC-JWT lane's marker fence stand in for it ([details](SD-JWT-VC#w3c-credentials-secured-as-sd-jwt-vcsd-jwt)) |
| Replay an SD-JWT VC + KB-JWT from another session, or relay one made for another verifier, to a caller that passed only `audience` or only `nonce` | Half-checked holder binding (`key_bound=True` after checking one of the two values) | A present KB-JWT is checked against `aud` **and** `nonce` together (RFC 9901 §7.3 step 5.6). Passing exactly one of them, or an empty one, raises `ClaimsInvalid` before any KB-JWT crypto runs. That stops a misleading flag; it does not stop the replay by itself, since a stripped KB-JWT still verifies with `key_bound=False`. `require_key_binding=True` (or checking `key_bound`) does. With neither value, `key_bound=True` is documented as possession only ([details](SD-JWT-VC)) |
| Wrap an SD-JWT VC + KB-JWT made for another verifier inside their own, correctly bound `jwt_vc_json` / `ldp_vc` presentation | Borrowed holder binding (a nested `key_bound=True` that vouches for a proof made for someone else) | A KB-JWT nested in a W3C presentation, bare or enveloped, must carry the **same** `aud` + `nonce` as that presentation (VP-JWT `aud` / `nonce`, Data Integrity `domain` / `challenge`), or the whole response is rejected. A nested SD-JWT without a KB-JWT is rejected unless the query opts out of holder binding, and then reports `key_bound=False` ([details](Presentations#sd-jwt-vcs-nested-in-a-w3c-presentation)) |
| Wrap a credential issued to someone else (a VC-JWT, a Data Integrity VC, or an SD-JWT VC with its KB-JWT stripped) inside their own, correctly bound `jwt_vc_json` / `ldp_vc` presentation | Present a victim's credential as their own (a relay by a verifier that once received it) | DCQL `require_cryptographic_holder_binding` (default `true`, OpenID4VP 1.0 §6.1) is enforced on the W3C formats: each embedded VC-JWT / Data Integrity VC must name the **authenticated** VP signer as its subject, and each nested SD-JWT VC must carry a KB-JWT bound to this exchange, or the whole response is rejected. A non-boolean flag is malformed, never coerced to `false` ([details](Presentations#holder-binding-on-the-w3c-formats)) |
| MITM a fetch | Tamper in transit | TLS with certificate validation and SNI on the pinned connection |
| Present a forged or replayed **key proof** to an issuer, to obtain a credential bound to a key they do not control | Wrong *issue* | `openvc.openid4vci`: the `openid4vci-proof+jwt` `typ` pin (no replaying a KB-JWT / VP-JWT / status-list token as a key proof), the allow-list before any crypto, **exactly one** of the `jwk`/`kid`/`x5c` header key parameters (two lets an attacker pair an honest `kid` with their own `jwk`), the key↔`alg` (kty, crv) binding, `aud` pinned to this Credential Issuer with a multi-valued `aud` rejected, and **`iat` freshness both ways** (a future-dated proof would otherwise never expire). Nonce single-use is the caller's, injected as a **required** callable and consumed once, after every signature verifies. A proof carrying a `key_attestation` must be signed by one of its `attested_keys` — but that check is **conformance, not defence**: the attestation's own signature is never verified, so a forger attests their own key; it catches an honest wallet, or your resolver, yielding a key the wallet never claimed. Believing an attestation is your job |

## Design posture

- **Fail closed.** Ambiguity, an unresolvable key, a malformed timestamp, an
  unrecognised status/schema shape, or a missing opted-in resolver all *reject*
  rather than accept.
- **Least authority on the network.** Every dereference is https-only and
  SSRF-guarded by default; nothing is fetched from an allow-list openvc did not vet.
- **HSM-friendly.** Key material need never enter the process.

## Observability

openvc is silent and dependency-free by default: it attaches a `NullHandler` to the
`openvc` logger and uses a no-op span hook. Two opt-ins let an operator see *why* a
verification accepted or rejected a credential, without pulling in a tracing dependency.

<!-- docs: no-run -->
```python
import logging
from openvc.observability import set_span_hook

# 1. Structured logs: the "openvc" logger is silent until you attach a handler.
logging.getLogger("openvc").setLevel(logging.DEBUG)
logging.basicConfig()

# 2. Spans: bridge to your tracer (OpenTelemetry, ...); a no-op until set.
set_span_hook(lambda name, attrs: tracer.start_as_current_span(name, attributes=attrs))
```

Neither logs nor spans carry credential contents or private key material — only format,
DIDs and outcomes — so enabling them does not widen the attack surface. See the
[Observability API](https://luisgf.github.io/openvc/api/observability/).

## Out of scope

- Compromise of a trusted anchor, of the host, or of the `SigningKey` backend.
- Availability of remote issuers / status lists (openvc bounds *its own* resource
  use — response size, decompressed size, recursion — but cannot guarantee a third
  party is reachable).
- Anything an **injected** resolver does after openvc hands it a URL, if the caller
  supplies a custom one instead of the guarded default.
- Side-channels in the underlying `cryptography` / `pyjwt` primitives.
